# 0.09 设计与规划

**目标：只做设计与规划，不改代码。** 为 0.10 上架 GitHub 做准备。

本文件是讨论稿，不是施工单。每一项都标了「建议 / 依据 / 风险」，等你确认后再落代码。

---

## 0. 先纠三个事实（都是这轮核查发现的）

在讨论 UI 之前，有三件事必须先说清楚，否则后面的设计会建在错的前提上。

### 0.1 评测站的判定从 4 种变成了 5 种

站方规范定义的是**五状态**，但我们代码里只实现了 4 种：

```js
// index.js:187 —— 注释写着 five，数组只有 4 个
const VERDICTS = ['helpful', 'harmful', 'no-difference', 'undetermined']
// 实际线上还有第五种：untestable
```

**实测数据（本次拉取，共 100 篇报告）：**

| 判定 | 数量 |
|---|---|
| `undetermined` 还说不准 | 55 |
| `helpful` 真有用 | 26 |
| `harmful` 帮倒忙 | 12 |
| `no-difference` 没啥差别 | 4 |
| **`untestable` 没法测** | **3** ← 我们没处理 |

**后果**：这 3 篇报告对应的插件，徽章会调用 `t('review.untestable')`，而中英文词典里都没有这个词条，界面会**原样显示 `review.untestable` 这个 key 字符串**。

**建议**：这是 bug，不是设计问题，建议在 0.10 前修掉（补一个枚举值 + 两条文案）。或者随 0.09 的实现一起修。

### 0.2 报告数从 67 涨到 100

上次对接时是 67 篇，现在是 100 篇。这说明站方在持续产出，我们的缓存策略（30 分钟）和全量拉取（100 次详情请求）需要重新评估性能。

**建议**：把「全量拉详情」改为「列表 + 按需拉详情」，或至少把并发从 6 提到 8–10，并加一次耗时测量。

### 0.3 评测站没有我们想要的结构化档位

之前就确认过，这次再次核实：`/api/plugins` 返回的字段里**没有 tier / 安全结论**，只有 `publicReviewCount`。档位仍然只能从标题正则解析。

## 1. UI 设计

### 1.1 现状盘点

| 指标 | 数值 |
|---|---|
| `index.js`（Host） | 2796 行 |
| `client.js`（界面） | 4055 行 |
| CSS 类 | 93 个 |
| 文案键 | 约 200 个 × 中英两份 |
| 界面组件 | 11 个（抽屉、卡片、分页、进度、账号…） |

功能是全的，问题是**结构**。

### 1.2 问题一：底部是一条会互相挤的堆栈

当前弹窗从下往上的固定层级：

```
页脚         共 6032 条 · 第 1/252 页
OutcomeBar   已生效 / 失败
ProgressPanel 正在安装… › 取消
确认栏        确认导入 xxx
详情抽屉      （absolute 覆盖，不占位）
语言圆钮      （absolute）
```

最坏情况（安装进行中 + 上一次有结果 + 确认栏同时存在）时，底部会堆 3 条横幅。窗口高度固定 `min(84vh, 760px)`，列表只剩不到 200px。

**这解释了你之前说的"安装卡住"观感**：界面在安装前后不断长高又缩回，看起来像卡住了。

**建议：底部状态收成一条**，同一时刻只显示优先级最高的一个：

```
优先级：进度（安装中）> 确认（待确认）> 结果（已结束）
```

其余内容折叠进这条右侧的「详情」展开。用户永远只面对一件要处理的事。

**风险**：现有代码里 `OutcomeBar` / `ProgressPanel` / 确认栏是三段独立 JSX，合并要改动 `MarketModal` 的尾部结构。属于中等改动。

### 1.3 问题二：抽屉遮住列表

```css
.dpm-drawer{position:absolute;right:0;width:min(380px,54%)}
```

54% 在窄窗口下几乎全遮，而且因为不占位，列表不会重排——用户点开详情就"看不见自己在逛什么了"。

**建议**：宽窗口改并排（`grid-template-columns: 1fr 380px`），窄窗口（< 720px）才退回覆盖。

**收益**：能一边看列表一边对比详情，这才是"逛市场"该有的姿势。

**风险**：`dpm-panel` 是 flex column，改 grid 会牵动 header/body/footer 的排列。需要重画整个面板布局。

### 1.4 问题三：卡片信息权重是平的

一张卡片上现在同时出现：评审徽章、档位、⚠、扫描状态、分类、最多 6 个能力标签、2 条红线、已安装标记、版本徽章、作者、星标、下载、语言、两行摘要。

**93 个 CSS 类里有 15 个是 `.dpm-tag` 的变体**，这本身就是信号：我们在用同一种视觉元件承载完全不同权重的信息。

**建议按"决策顺序"重排，而不是按"数据获得顺序"：**

```
┌─────────────────────────────────────────────┐
│ dsh-project-memory              [安装 v0.6.3]│  ① 它是什么 + 装不装
│ 项目级持久记忆，任务自动沉淀…      （一行截断）  │
│                                              │
│ [已测评·真有用] [深度审计]        ★ 23        │  ② 能不能信（最多 2 个徽章）
│                                              │
│ @00080000 · 1 天前更新                        │  ③ 谁做的、新不新
└─────────────────────────────────────────────┘
     能力清单、红线、分类 → 收进抽屉
```

**具体规则**：
- 列表最多 2 个徽章：**一个判定 + 一个档位**
- 能力标签、红线**不在列表显示**，只在抽屉里；列表若存在红线，只留一个 `⚠`
- 分类不占列表位置（分类本来就在筛选栏选过了）

**风险**：这是纯视觉改动，但要重写 `EntryCard` + `Tags`，且会改变用户已有的扫视习惯。

### 1.5 问题四：硬编码深色，亮色主题会翻车

```css
/* 4 处写死 #17181c，3 处写死 #fff */
.dpm-button[data-kind="primary"]{background:#17181c;color:#fff}
.dpm-pager-btn[data-active="true"]{background:#17181c;color:#fff}
.dpm-lang button[data-active="true"]{background:#17181c;color:#fff}
```

深色主题下没问题。**上架后别人用亮色主题**会看到高对比黑块，与周围 `var(--dsw-alias-*)` 的风格割裂。

**建议**：改用 `var(--dsw-alias-brand-primary)`，或加 `[data-theme="light"]` 覆盖。

### 1.6 新增：截图画廊（你已确认要做）

**数据前提（已核实）**：
- 6084 个插件里 **1328 个有截图**（21.8%）
- 来源是 `raw.githubusercontent.com`，是外链
- 多数 1–3 张，最多 5 张

**设计**：

```
详情抽屉
├─ [缩略图条]  ← 仅在 screenshots 非空时渲染
│   ▢ ▢ ▢     点击 → 大图
├─ 介绍
├─ 作者
├─ 安装源
├─ 向作者提问
└─ 版本历史
```

**规则**：
- 无截图 → **整块不渲染**（不占位、不显示"暂无截图"）
- 图片加载失败 → 静默隐藏该张，不显示裂图
- 外链风险：`referrerPolicy="no-referrer"`，加 `loading="lazy"`
- 不做全屏灯箱（超出本版范围）

**风险**：`raw.githubusercontent.com` 在部分网络可能被墙。建议**只做一个降级方案**：加载失败就隐藏，不阻塞详情其他内容。

## 2. 与评测团队的合作方向

### 2.1 边界先说清楚

**我们只有"爬取公开信息"的授权**，不参与评测、不做二次审查。

所以所有合作都必须满足：
- 数据来自对方公开 API
- 我们不修改、不重新判定、不发布结论
- 不做评分/星级（站方规范明确禁止）

### 2.2 核心判断：市场缺的不是数据，是"在正确的时机呈现"

现在市场有的：作者、星标、版本、判定、档位。
现在市场**没用好**的：判定只是彩色标签，用户装之前不会真的读。

**实测**：100 篇报告里 **12 篇判定是 `harmful`（帮倒忙）**。这些插件现在只是挂个红标，用户点「安装」照样一路装进去。

### 2.3 提案 A（你已选定）：安全闸门

**把 `harmful` 从"标签"变成"闸门"。**

```
用户点 [安装]
   ↓
该插件有 harmful 报告？
   ├─ 否 → 现有确认栏（不变）
   └─ 是 → 确认栏强制展开：
           ┌─────────────────────────────────────┐
           │ ⚠ 这个插件被独立测评判定为「帮倒忙」    │
           │                                     │
           │ dsh-deja 0.22.2 测评：跨 41 个智能体的 │
           │ 历史检索很好用，但默认一次召回就吐     │
           │ 28 万 token                          │
           │                                     │
           │ 测评者 IKsi · 2026-10-19             │
           │ [阅读完整报告]                        │
           │                                     │
           │ ☐ 我已阅读，仍要安装                   │
           │           [取消]  [确认安装(禁用)]     │
           └─────────────────────────────────────┘
```

**规则**：
- 勾选「我已阅读」才能点确认
- 每行最多展示 1 篇 harmful 报告（最新那篇），其余给「还有 N 篇」
- 不改动数据来源，只用已有字段
- 不做"阻止安装"——最终决定权仍在用户

**为什么值得做**：这是唯一一个把"评测数据"真正用在**决策时刻**的设计。现在的标签是在用户不看的地方说话。

**风险**：会让安装流程多一步。建议只在 `harmful` 时触发，`undetermined` / `helpful` 不拦。

### 2.4 提案 B（暂缓）：请对方加结构化字段

想请站方加：

```json
"securityVerdict": "pass" | "fail" | "unrated",
"reviewTier": "deep" | "standard" | "quick" | "self",
"capabilitiesTested": ["fs-write", "network"]
```

**理由**：现在 38 篇报告的档位只能靠标题正则猜（`【深度审计】` 等），这是市场最脆的一环。

**为什么暂缓**：你选了"只做 A"。这项需要你去和对方谈，不是我能单方面完成的。

### 2.5 提案 C（暂缓）：双向互链

市场详情 → "查看 N 篇独立评测" → 站方
站方页面 → "在插件市场查看" → 市场

**收益**：他们得到导流，我们得到可信度背书，且完全在爬取授权内。

**为什么暂缓**：同上，需要对方配合。

### 2.6 明确不做的三件事

| 不做 | 原因 |
|---|---|
| 二次评测 | 站方给报告、我们不审，这是你定的边界 |
| 评分 / 星级 | 站方规范明令禁止，跟着做等于拆台 |
| 爬全文正文 | 现在只取元数据（标题/判定/作者/时间），全文涉及版权 |

## 4. 建议的落地顺序（供 0.10 排期参考）

按「风险低 → 风险高」和「收益大 → 收益小」排：

| 顺序 | 项 | 收益 | 风险 | 工作量 |
|---|---|---|---|---|
| 1 | 补 `untestable` 判定（0.1 的 bug） | 修可见错误 | 低 | 极小 |
| 2 | 截图画廊 | 大 | 低 | 小 |
| 3 | 硬编码颜色 | 中 | 低 | 小 |
| 4 | 安全闸门（提案 A） | **大** | 中 | 中 |
| 5 | 底部状态收成一条 | 中 | 中 | 中 |
| 6 | 卡片信息重排 | 中 | 中 | 中 |
| 7 | 抽屉改并排 | 中 | 高 | 大 |
| 8 | 发布元数据补全 | 必须 | 低 | 小 |

**我的建议**：1 → 2 → 3 → 4 一起做，构成一个可上架的完整版本；5/6/7 属于长期结构改造，可以放到 0.11。
